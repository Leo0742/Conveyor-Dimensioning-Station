# Conveyor Dimensioning Station

Прототип станции для автоматического измерения габаритов товара на конвейере по 3D-профилям.

Я сделал этот проект для тестового задания Ozon Tech × Университет Иннополис, трек «Компьютерное зрение», вариант 1. Цель — пройти весь путь от выбора оборудования и расчёта компоновки до измерения облака точек, проверки результата и формирования сообщения для WMS.

**Главный файл для сдачи:** [полный отчёт в PDF](docs/report.pdf)

Дополнительные материалы: [сравнение оборудования](docs/hardware_trade_study.md) · [источники](docs/references.md) · [проверка частоты профилей](docs/evidence/lmi_profile_rate_verification.md)

> Проект не выдаёт синтетические тесты за физическую метрологию. Реального Gocator у меня не было, поэтому точность всей станции и целевые 1000 профилей/с нужно подтвердить на оборудовании.

## Задача

Исходные условия:

- ширина ленты — **600 мм**;
- скорость — **1 м/с**;
- товар — от **10×10×10** до **400×300×300 мм**;
- средний интервал между товарами — около **3 с**;
- допустимая ошибка каждой стороны — `±max(5%, 5 мм)`;
- результат нужно передать в WMS.

Для произвольной ориентации товара нужен ориентированный ограничивающий параллелепипед. В прототипе используется приближённый OBB; точный минимум объёма перед физической приёмкой нужно проверить отдельно.

## Моё решение

Я остановился на одном **LMI Gocator 2880** с двумя камерами в одном корпусе.

Предварительная компоновка:

- FOV на уровне верхней грани товара (Z=300 мм) — **680 мм**;
- запас относительно 600-мм ленты — **40 мм с каждой стороны**;
- расчётная высота сенсора над лентой — **≈916,7 мм**;
- целевой шаг по Y — **1 мм**;
- датчик присутствия — **SICK WLF4FI-973121A0ZZZ**;
- энкодер — **SICK DFS60I-BHPC65536**;
- локальный вычислитель — **OnLogic Karbon K801**.

Почему 2880:
1. две камеры уменьшают тени от стенок товара;
2. одного корпуса достаточно для нужной ширины;
3. не нужна взаимная калибровка двух независимых профилометров;
4. по расчёту остаётся достаточная дискретизация для 10-мм объекта.

Расчётная геометрия — это не монтажный чертёж. Финальные координаты должны определяться по заводской калибровочной модели конкретного сенсора.

## Как работает прототип

```text
WLF4FI ──> событие товара
DFS60  ──> координата Y
                │
Gocator 2880 ──> X-Z профили
                │
                v
          OnLogic K801
          ├─ калибровка
          ├─ удаление плоскости ленты
          ├─ фильтрация и кластеризация
          ├─ оценка OBB
          ├─ проверка качества
          └─ локальная очередь
                │
                v
               WMS
```

Основные шаги в коде:

1. RANSAC оценивает плоскость пустой ленты.
2. Точки ленты удаляются, затем применяется фильтрация выбросов.
3. Радиус кластеризации выбирается по расстоянию между наблюдаемыми точками.
4. Два значимых кластера дают статус `object_overlap`.
5. Для одного товара оценивается OBB и сравниваются два способа ориентации.
6. При недостаточном качестве возвращается явный статус вместо «уверенного» размера.
7. Валидные окна можно объединить медианой.
8. Для WMS формируется JSON; при ошибочном статусе размеры наружу не отправляются.

Стороны в текущем PoC нормализуются как `L ≥ W ≥ H`. Если контракт WMS требует, чтобы `H` всегда означала именно вертикальную ось Z, правило именования нужно изменить отдельно — геометрический OBB от этого не меняется.

## Что реализовано

- упрощённая модель линейного 3D-профилометра с двумя ракурсами;
- коробки, L-образные призмы, цилиндры и составные формы;
- шум, пропуски точек и целых профилей, ограничение FOV и частичная видимость;
- RANSAC плоскости, фильтрация, кластеризация и обработка нескольких объектов;
- приближённый OBB и сравнение с Open3D как независимой проверкой;
- статусы `ok`, `insufficient_depth_data`, `object_overlap`, `calibration_error`, `measurement_out_of_range`, `low_confidence`;
- простая эвристика качества (это **не вероятность правильности**);
- WMS-модель и локальная JSONL-очередь;
- CLI, тесты, фиксированные benchmark-сценарии, Monte Carlo и multi-frame demo.

## Результаты синтетической проверки

Финальный Monte Carlo содержит **500** сценариев. Из них **475** должны были быть измеримыми, ещё **25** специально сделаны как сценарии для отбраковки.

| Метрика | Результат |
|---|---:|
| Корректных `OK` | 427 |
| Неверных `OK` | 27 |
| Отклонённых валидных сценариев | 21 |
| Доля принятых валидных сценариев | 95,6% |
| Точность среди принятых | 94,1% |
| Доля корректных измерений | 89,9% |
| Специальные reject-сценарии | 25/25 отклонены |

Для сложного поднабора `tilted/irregular` точность среди принятых — **84,9%**, а доля корректных измерений — **72,0%**. Я не скрываю эти случаи: они показывают слабые места видимости и упрощённой модели опоры.

Эти числа относятся только к программной проверке на синтетических данных. Они **не являются гарантией точности физической станции**.

## Быстрый запуск

Нужны Python 3.12 и [uv](https://docs.astral.sh/uv/).

```bash
uv sync --frozen --python 3.12
uv run pytest -q
uv run ruff check .
uv run conveyor-dimensioning demo --output-dir assets/demo --seed 42
```

Проверить один сохранённый пример:

```bash
uv run conveyor-dimensioning measure assets/demo/sample_scene.npz \
  --item-id synthetic-check --seed 42
```

Запустить финальный Monte Carlo:

```bash
uv run conveyor-dimensioning monte-carlo \
  --output-dir assets/demo \
  --count 500 \
  --seed 20261017
```

Сравнение OBB с Open3D:

```bash
uv sync --frozen --python 3.12 --extra open3d
uv run python scripts/compare_obb.py --output assets/demo/obb_comparison.json
```

## Ограничения

Перед реальным внедрением нужно проверить то, чего синтетический PoC не доказывает:

- достижимость **1000 профилей/с** при реальной экспозиции и активной области Gocator 2880;
- абсолютную погрешность станции на калибровочных объектах и реальном ассортименте;
- чёрные, глянцевые, прозрачные и мягкие товары;
- скрытое дно и глубокие поднутрения;
- устойчивость к вибрации, загрязнению окна и дрейфу калибровки;
- ошибку приближённого OBB относительно более точного алгоритма минимального объёма.

Симулятор специально упрощён: он не моделирует BRDF, speckle, multipath, насыщение и преломление прозрачной упаковки.
