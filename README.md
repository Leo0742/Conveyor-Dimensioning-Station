# Conveyor Dimensioning Station

[![CI](https://github.com/Leo0742/Conveyor-Dimensioning-Station/actions/workflows/ci.yml/badge.svg)](https://github.com/Leo0742/Conveyor-Dimensioning-Station/actions/workflows/ci.yml)

Для тестового задания Ozon Tech × Университет Иннополис я спроектировал станцию,
которая измеряет габариты товара на движущемся конвейере. В репозитории есть
сравнение датчиков, расчёт компоновки и синтетический Python-прототип измерительного
алгоритма: от облака точек до сообщения для WMS.

Все опубликованные метрики получены на синтетике. Физический Gocator и конвейер
не испытывались, поэтому абсолютная точность production-станции не заявляется.

**[Полный технический отчёт (PDF)](docs/report.pdf)**

![Синтетический пример измерения](assets/demo/measurement.png)

## Задача

Требуется измерять L×W×H товаров от 10×10×10 до 400×300×300 мм на ленте
шириной 600 мм при скорости 1 м/с. Допуск для каждой стороны —
`±max(5 %, 5 мм)`, результат нужно передать в WMS.

По условию габариты задаются сторонами охватывающего прямоугольного параллелепипеда
минимального объёма. В программном PoC используется приближённый OBB; перед
физической приёмкой его ошибку нужно сравнить с точной или эталонной реализацией
minimum-volume box.

## Решение

Я выбрал один двухкамерный лазерный профилометр **LMI Gocator 2880**. Товар
обнаруживает **SICK WLF4FI**, а **SICK DFS60** с мерным колесом задаёт координату
по движению. Профили предполагается обрабатывать локально на **OnLogic Karbon K801**,
после чего формируется сообщение для WMS.

Почему 2880:

- две камеры в одном калиброванном корпусе уменьшают затенение боковых граней;
- расчётный FOV 680 мм на высоте товара 300 мм оставляет по 40 мм запаса с каждой стороны;
- предварительная высота монтажа — около 916,7 мм над лентой;
- один 2880 проще синхронизировать и калибровать, чем два встречных Gocator 2490.

Целевые 1000 профилей/с дают шаг 1 мм по Y, но этот режим ещё нужно проверить
в Gocator Emulator или на реальном датчике. Расчёт FOV и высоты — предварительная
компоновка, а не замена заводской калибровочной модели.

## Как устроено решение

Проектный поток данных для физической станции:

```text
WLF4FI + DFS60 → Gocator 2880 → профили X–Z → облако точек
→ удаление ленты → фильтрация и кластеры → OBB → проверка результата
→ сообщение для WMS
```

Кодовый PoC в этом репозитории не подключён к реальным WLF4FI/DFS60/Gocator.
Он начинает с уже сформированного или синтетически сгенерированного `points_mm`:

```text
points_mm → RANSAC плоскости ленты → фильтрация → кластеры
→ оценка контакта с лентой → приближённый OBB → статусы/quality checks
→ WMSMessage JSON и локальная JSONL-очередь
```

Таким образом, репозиторий проверяет геометрию и программный путь обработки,
а аппаратный адаптер Gocator/PLC и сетевой транспорт в реальную WMS остаются
частью следующего этапа.

## Что реализовано

В коде есть:

- упрощённая модель линейного профилометра с шагом по FOV/частоте, двумя ракурсами,
  шумом, пропусками точек и целых профилей;
- RANSAC плоскости ленты, фильтрация, кластеризация и обнаружение двух товаров;
- эвристика контакта с опорной плоскостью и приближённый OBB минимального объёма;
- статусы и проверки качества, WMS-схема и локальная JSONL-очередь;
- модель границы acquisition batch с encoder/profile-quality метаданными без
  имитации реального драйвера;
- регрессионные тесты, тест упрощённой модели сенсора, Monte Carlo benchmark
  и multi-frame demo.

PoC передаёт в WMS отсортированные рёбра OBB: `length_mm ≥ width_mm ≥ height_mm`.
Это не привязка к X/Y/Z. Вертикальный габарит станции отдельно ограничен 300 мм;
если production WMS понимает `height_mm` именно как ось Z, нужен явный другой маппинг.

Multi-frame итог использует только окна `status=ok`: требуется минимум 3 окна,
не менее 50% валидных и по каждой стороне
`MAD ≤ max(2,5 мм; 2,5% медианы)`. Иначе результат не получает статус `ok`.

Для физической станции ещё нужны адаптер Gocator/PLC, стендовая калибровка,
транспорт в WMS по HTTPS/mTLS с повторами, мониторинг и механика отвода товара
на ручной поток.

## Результаты

На зафиксированном синтетическом наборе (`seed=20261018`):

| Всего | Валидных сценариев | Корректных `OK` | Ошибочных `OK` | Отклонено валидных | Доля принятых | Точность среди принятых | Доля корректных измерений |
|---:|---:|---:|---:|---:|---:|---:|---:|
| 500 | 475 | 412 | 28 | 35 | 92,6% | 93,6% | 86,7% |

Доля принятых показывает, сколько валидных сценариев алгоритм не отклонил.
Точность среди принятых — доля корректных результатов среди выданных `OK`.
Все 25/25 искусственных сценариев, которые должны были быть отклонены, действительно
получили защитный отказ.

Прежний final seed `20261017` аннулирован, потому что исправление физического
footprint изменило генератор. Параметры были заморожены до единственного прогона
нового final seed `20261018`; после просмотра результата пороги не менялись.

Самый сложный по acceptance срез — наклонённые и нерегулярные объекты: 89,4%
precision among accepted и 74,4% correct measurement rate. В noisy/incomplete
срезе precision among accepted равен 84,0%. Это результаты проверки программной
геометрии на синтетике, а не оценка точности физической станции.

## Запуск

Ниже — самый простой способ проверить проект с нуля. Команды нужно копировать в
терминал **по одной, сверху вниз**. После каждой команды дождитесь её завершения и
только потом переходите к следующей.

Для быстрой проверки проекта достаточно выполнить **шаги 1–6**. Шаг 7 содержит
дополнительные проверки и для первого запуска не обязателен.

### 1. Проверить, что установлены Git и uv

В терминале выполните:

```bash
git --version
```

Затем:

```bash
uv --version
```

Если обе команды выводят номер версии, можно переходить к следующему шагу.

Если `uv` не установлен:

- macOS / Linux:

  ```bash
  curl -LsSf https://astral.sh/uv/install.sh | sh
  ```

- Windows PowerShell:

  ```powershell
  powershell -ExecutionPolicy ByPass -c "irm https://astral.sh/uv/install.ps1 | iex"
  ```

После установки закройте и снова откройте терминал, затем ещё раз выполните
`uv --version`. Если не установлен Git, его можно скачать с
[git-scm.com](https://git-scm.com/downloads).

### 2. Скачать проект

```bash
git clone https://github.com/Leo0742/Conveyor-Dimensioning-Station.git
```

После завершения клонирования перейти в папку проекта:

```bash
cd Conveyor-Dimensioning-Station
```

Все следующие команды нужно выполнять **из этой папки**.

### 3. Установить Python 3.12 и зависимости проекта

```bash
uv sync --frozen --python 3.12
```

`uv` создаст локальное окружение проекта и при необходимости установит подходящий
Python 3.12. На этом шаге нужно дождаться полного завершения установки.

### 4. Проверить код и тесты

Сначала запустить Ruff:

```bash
uv run ruff check .
```

При успешной проверке Ruff должен завершиться без ошибок.

Затем запустить автоматические тесты:

```bash
uv run pytest -q
```

В базовой установке Open3D не ставится специально, поэтому один optional-тест
будет пропущен. Это нормально: отдельная полная проверка с Open3D описана ниже.

### 5. Запустить основное демо

Для локальной проверки результаты лучше сохранять отдельно от зафиксированных файлов
репозитория. Папка `outputs/` уже добавлена в `.gitignore`, поэтому эти запуски не
изменяют сохранённые demo-артефакты.

```bash
uv run conveyor-dimensioning demo --output-dir outputs/demo --seed 42
```

После выполнения откройте папку `outputs/demo/`. Должны появиться:

- `measurement.png` — визуализация измерения;
- `conveyor_demo.gif` — движение товара по конвейеру;
- `sample_scene.npz` — синтетическое облако точек для повторного измерения;
- `example_measurement.json` — пример сообщения для WMS.

Если эти четыре файла созданы, демо отработало корректно.

### 6. Повторно измерить сохранённую сцену

Эта команда использует `sample_scene.npz`, созданный на предыдущем шаге:

```bash
uv run conveyor-dimensioning measure outputs/demo/sample_scene.npz --item-id synthetic-check --seed 42
```

В терминале появится JSON с результатом измерения. Для нормального демо-сценария
поле `measurement_status` должно быть `"ok"`.

### 7. Запустить дополнительные проверки

Эти команды не обязательны для первого знакомства с проектом. Их можно запускать
по одной после выполнения шагов 1–6.

Тест упрощённой модели сенсора:

```bash
uv run conveyor-dimensioning sensor-benchmark --output-dir outputs/demo --seed 42
```

Полный Monte Carlo на 500 сценариев может выполняться несколько минут:

```bash
uv run conveyor-dimensioning monte-carlo --output-dir outputs/demo --count 500 --seed 20261018
```

Демонстрация измерения по нескольким окнам движущегося товара:

```bash
uv run conveyor-dimensioning multiframe-demo --output-dir outputs/demo --seed 42
```

Результаты этих запусков также сохраняются в `outputs/demo/`.

<details>
<summary>Дополнительно: проверка OBB через Open3D</summary>

Open3D не нужен для основного алгоритма и поэтому вынесен в optional-зависимость.
Пакет большой, поэтому его первая установка может занять больше времени, чем обычный
`uv sync`. Этот сценарий отдельно проверяется в CI на Ubuntu + Python 3.12.

Сначала установить дополнительные зависимости:

```bash
uv sync --frozen --python 3.12 --extra open3d
```

После установки повторно запустить весь набор тестов:

```bash
uv run pytest -q
```

В этом режиме все тесты, включая Open3D-сравнение, должны пройти без пропусков.

Затем выполнить независимое сравнение OBB:

```bash
uv run python scripts/compare_obb.py --output outputs/demo/obb_comparison.json
```

После выполнения будет создан или обновлён файл `outputs/demo/obb_comparison.json`
с результатами для шести форм: `box`, `rotated_box`, `l_prism`, `cylinder`,
`composite` и `convex_irregular`.

В зафиксированном окружении используется Open3D 0.19.0. Его доступный reference-метод —
`create_from_points_minimal (minimal-approx)`, поэтому это сравнение используется как
независимая проверка приближённого OBB, а не как доказательство математически точного
minimum-volume box.

</details>

## Ограничения

Симулятор не является Gocator Emulator и не моделирует реальную оптику чёрной,
глянцевой и прозрачной упаковки. Скрытое дно не восстанавливается; оценка контакта
с опорной плоскостью остаётся эвристикой. OBB в PoC — приближённый, а `confidence` —
некалиброванный показатель качества, не вероятность. Реальная отправка по HTTPS/mTLS
не реализована: PoC формирует WMS-сообщение и локальную очередь. Абсолютную
погрешность физической станции можно подтвердить только на стенде через калибровку
и MSA/Gage R&R.

Надёжное срабатывание WLF4FI на минимальном 10-мм товаре также требует стенда:
влияют размер светового пятна, расстояние и отражательная способность. Возможные
fallback — иная геометрия установки, меньший spot, световая завеса или
presence-логика по PLC/потоку профилей.

Подробное [сравнение оборудования](docs/hardware_trade_study.md), схема станции,
метрологические ограничения, план ML-fallback и физической валидации собраны
в [отчёте](docs/report.pdf).
